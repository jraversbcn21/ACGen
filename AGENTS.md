## Architecture

- **React 18 SPA**, Vite 5, TypeScript. 100% static deploy. All core logic in-browser.
- **Hash-based routing** (`#/landing`, `#/acceptance`, `#/testcase`, etc.) via `getViewFromHash()` + `hashchange` listener. `navigate(view, { prefill? })` callback. Browser back/forward and F5 work.
- **ViewType**: `'landing' | 'acceptance' | 'testcase' | 'bugreport' | 'testdata' | 'sprinttracker' | 'regressiontracker' | 'userstory' | 'refiner' | 'edgecase' | 'converter' | 'designvalidator'`
- **App shell**: `<I18nProvider>` > `<div className="page">` > `<Header>` + `<div className="app-layout">` > `<Sidebar>` + `<main className="container">`. Sidebar hidden on landing.
- **Sidebar**: collapsible icon-nav grouped by category (Generar/Refinar/Convertir/Seguimiento) + active workspace name + prompt editor link. Active highlight via hash.

### Confidential mode (Modo confidencial)

### Backup & persistence

- `src/services/backup.ts` — pure logic core, no React. `collectBackupData({includeApiKeys?})` snapshots every `acgen_*` localStorage entry verbatim (no `JSON.parse` — values are heterogeneous JSON/raw-string/bare-literal), always excludes `acgen_last_backup`, excludes the API-key family (`acgen_key_*` + legacy `acgen_api_key`, matched via `isSensitiveKey`) unless opted in. `createBackup(opts)` wraps that into a pretty-printed `{schemaVersion: 1, exportedAt, data}` JSON string (`BACKUP_SCHEMA_VERSION`). `parseImportFile(json)` classifies an imported file as `backup` / `legacyWorkspace` (pre-dates this feature — single-workspace export, recognized by `id`+`name`+`artifacts[]` shape) / `futureVersion` / `invalid` (`json` or `structure` reason). `restoreBackup(backup)` is a total replace of the current `acgen_*` state with the backup's `data`: always preserves `acgen_last_backup`, preserves local API keys when the backup itself carries none, rejects tampered entries whose key doesn't start with `acgen_`, never touches non-`acgen_` keys, and on `QuotaExceededError` rolls back to the exact pre-restore snapshot and returns `{ok: false, error: 'quota'}`. Plus reminder logic: `hasSignificantData()` (true if any workspace has an artifact, any sprint exists, the regression board has a filled cell or an archived run, or criteria/bug history has an entry — corrupt JSON in any one source counts as "no data" for that source, not a throw), `isBackupDue(lastBackupAt, now?)` (true when there's significant data and either no backup was ever made or the last one is older than `BACKUP_REMINDER_DAYS` = 7), `getLastBackupAt()`/`markBackupDone(now?)` over `acgen_last_backup`.
- `src/hooks/useBackupReminder.ts` — thin `useLocalStorage(STORAGE_KEYS.LAST_BACKUP, null)` wrapper exposing `{due, lastBackupAt, markDone}`; `due` is `isBackupDue(lastBackupAt)` recomputed on every render.
- `src/components/BackupMenu.tsx` — dropdown mounted in `Header` next to `WorkspacePicker` (💾 icon, reminder badge when `due`). Export: checkbox "incluir API keys" (plain-text warning shown when checked) → `createBackup` → `downloadJson`/`toFilename` → `markDone()`. Import: reads the file, `parseImportFile` routes it — `backup` goes through an inline 2-step confirm (`backup.confirmReplace` / yes / cancel) before `restoreBackup` + `onRestored` (defaults to `location.reload()`); `legacyWorkspace` calls `onImportLegacyWorkspace` (wired to `useWorkspace.importWorkspace` in `App.tsx`) directly, no confirm — wrapped in try/catch because `parseImportFile`'s shallow shape check accepts files `importWorkspace` still rejects (e.g. empty-string `id`): a throw shows `backup.importError` instead of failing silently; `futureVersion`/`invalid` show an `alert()`. A quota failure on confirm shows `backup.quotaError` and leaves the pending state so the user can retry or cancel.
- `src/services/autoBackup.ts` + `src/types/fileSystemAccess.d.ts` — File System Access API service (Chromium-only: `isFileSystemAccessSupported()` checks `'showSaveFilePicker' in window`). `chooseBackupFile()` opens the native save picker (`suggestedName: 'acgen-auto-backup.json'`), resolves `null` on user cancel (`AbortError`), otherwise propagates other errors. The chosen `FileSystemFileHandle` is persisted in IndexedDB (`saveHandle`/`loadHandle`/`clearHandle`, DB `acgen-backup` → store `handles`, fixed key `autoBackupFile`) since it's the only storage that survives a reload with a live handle. `ensurePermission(handle)` resolves readwrite permission, prompting via `requestPermission` if needed, falling back gracefully when `queryPermission`/`requestPermission` aren't implemented. `writeSnapshot(handle, contents)` never rejects — permission denial, a rejecting permission check (e.g. `SecurityError` without a user gesture, or a revoked handle), or any write I/O failure all resolve to `false` so callers can show a soft warning instead of crashing.
- `src/hooks/useAutoBackup.ts` — state machine `'unsupported' | 'off' | 'active' | 'permissionNeeded' | 'error'`. On mount, resolves a persisted handle without prompting for permission (that needs a user gesture). `enable()`/`disable()`/`reconnect()` are the only user-gesture entry points. While `active`, listens for `acgen-local-storage` (same-tab, fired by `useLocalStorage`) and the native `storage` (cross-tab) events and writes a snapshot debounced 5s (`DEBOUNCE_MS`) after the last change. Events whose changed key is `acgen_last_backup` are ignored (the CustomEvent's `detail.key` / `StorageEvent.key` identifies it; events with no key info fail open and schedule): without this filter, every successful snapshot's own `markDone()` write would re-trigger the listener and produce an infinite snapshot→`markDone`→snapshot loop rewriting the disk file every 5s. Skipping it loses nothing — `collectBackupData` excludes that key, so its change alone can never alter snapshot content. Every snapshot calls `createBackup({includeApiKeys: false})` — auto-backups never include API keys — and a successful write calls the `onSnapshot` callback (wired to `useBackupReminder().markDone` in `BackupMenu`) so auto-backups also satisfy the 7-day reminder. Guards a stale in-flight write: if the handle changed (or was cleared by `disable()`) while a debounced/`enable()` write was in flight, the result is dropped instead of resurrecting `'active'`. The auto-backup UI section in `BackupMenu` renders only when `isFileSystemAccessSupported()` is true — hidden entirely in Firefox/Safari.
- `src/services/persistence.ts` — `requestPersistentStorage()` calls `navigator.storage.persist()` once; resolves `false` (never throws) when the API is absent or `persist()` rejects. Invoked fire-and-forget (`void requestPersistentStorage()`) once at `App.tsx` mount to reduce the odds the OS evicts localStorage under storage pressure.
- **Known limitations (accepted, not bugs)**: `useSprints`/`useRegressions`/`useHistory` write `localStorage` directly without dispatching `acgen-local-storage`, so a change made only through those hooks doesn't trigger an immediate auto-backup snapshot — it's captured by the next change that does dispatch the event, or once the page reconnects. Auto-backup to a local file is Chromium-only (no File System Access API in Firefox/Safari). Changes made in the ~5s debounce window right before closing the tab can be missed by auto-backup. "Clear site data" wipes the IndexedDB handle (the auto-backup connection), though the file already written to disk survives — the user just has to re-pick it via `reconnect()`.

### Sprint Tracker

- Fully offline — no LLM dependencies
- **Schema-driven tabs and columns, like the Regression Tracker (Fase 5)**: tabs and each tab's columns come from `useSchema()` (`schema.sprint.tabs: SprintTabSchema[]`, `src/types/schema.ts`) instead of being hardcoded. A `SprintTabSchema` is a `SchemaEntry` (id/labelKey/label/hidden — same shape and same "id never changes, label wins over labelKey, hidden never deletes" rules as Regression's fields/platforms) that additionally carries its own `columns: SchemaEntry[]`. With nothing saved to `acgen_schema` the tabs and columns are exactly today's five: Resueltos, Creados, ReOpen, Prioridad Alta, JSD, each with its historical column set (JSD's grid is 6 columns wide but only 3 are named — see `colCount` below).
- **`TrackerGrid.tsx` (the spreadsheet shared with the Regression Tracker) takes a resolved `tabColumns: Record<T, {label, dataIndex}[]>` prop — it never sees the schema.** `SprintDashboard.tsx` is the resolver: for the active tab it maps every schema column to its own index in that tab's `columns` array (`dataIndex`, computed BEFORE filtering hidden entries — filtering first would silently shift every later column's data index onto the wrong cell) and only then drops the hidden ones. `TrackerGrid` just paints whatever `{label, dataIndex}` list it's handed, in that order, with zero schema awareness. A second prop, `tabColCount: Record<T, number>`, carries **how many columns the caller declares for that tab, hidden ones included** (`SprintDashboard` passes `tab.columns.length`; `RegressionTracker` passes `LEGACY_HEADERS.length`) — without it `TrackerGrid` cannot tell "extra unlabelled data column, must render" from "column the user just hid, must not", and hiding the last column of a tab silently did nothing. `colCount = Math.max(columns.length, grid[0]?.length ?? 0, 1)`: deriving column count from headers alone would hide any stored data column past the last known header — JSD ships 3 header columns over a 6-wide grid, so the `grid[0]?.length` floor keeps D/E/F rendering (unlabeled) instead of making their data vanish from the screen. The trailing unlabelled columns are appended starting at `Math.max(maxNamed + 1, declaredCount)`, and that `declaredCount` floor is exactly what stops a hidden last column from reappearing as an unlabelled one. Everything else indexes by `dataIndex` (data position), never by visual (on-screen) position: stored column widths (keyed `${tab}-${dataIndex}`), `cellRefs`, the `data-col` attribute, `onUpdateGridCell`'s `col` argument, and the A/B/C... column letters (`colToLetter(dataIndex)`) — hide column B and the remaining letters read A, C, D... not A, B, C. The one exception is ←/→ arrow-key navigation between cells, which walks the visual order (what's next to what on screen), because that's what a user pressing an arrow key expects.
- **Search divergence from the Regression Tracker is deliberate, not a bug**: `TrackerGrid`'s debounced (250ms) search matches every cell in the row array, hidden data columns included — a value sitting in a column the user hid still surfaces its row. This is the OPPOSITE of the Regression Tracker, where Fase 4 scoped search to only the schema's *visible* ticket fields. Jorge's call on 2026-08-15: hiding a column is a view preference, not a deletion, so the Sprint Tracker's search treats hidden data as still-searchable; the Regression Tracker's narrower Fase 4 behavior was left as-is rather than "fixed" to match. Pinned by `TrackerGrid.test.tsx`'s "tabColumns por indice de datos" describe block precisely so this divergence doesn't get flattened by someone reading the two trackers side by side. Also see "Known issues".
- **Cannot delete or reorder tabs/columns — deliberate, see "Known issues"**: the grid is positional (a column's screen position and its `dataIndex` are the same number), so either operation would require migrating to keyed rows plus migrating every stored width from index-keyed to id-keyed. Hiding already covers the practical case.
- **`useSchema()` normalizes each sprint tab to always have a `columns` array**: a hand-written or half-restored `acgen_schema` can carry `{"tabs":[{"id":"resolved","label":"R"}]}` — `Array.isArray(sprint.tabs)` is true so the per-list fallback doesn't fire, and `tab.columns.filter(...)` then threw inside `SprintSchemaEditor`, which `App.tsx`'s per-view `ErrorBoundary` turned into a dead Sprint Tracker view with the "Restaurar por defecto" escape hatch trapped inside the crashed component. Normalizing once in `useSchema`'s `useMemo` (`Array.isArray(t?.columns) ? t : { ...t, columns: [] }`, which also covers `columns` being some non-array) fixes every consumer at once instead of scattering `?? []` across the four call sites. Consequence worth knowing: the normalization is **write-through**. Callers write by spreading the object the hook returns (`setSchema({ ...schema, sprint: ... })`) and `setSchema` merges shallowly per section, so editing *any* tab re-persists *every* normalized tab. For a tab that was simply missing its `columns` key that is additive and harmless. **It is not harmless if `columns` ever holds a non-array with real content**: the normalization replaces it with `[]` in memory and the next schema write of any kind persists that, losing whatever was there. No path reaches this today (it needs a hand-edited `acgen_schema`), but **before Fase 6+ reuses the `columns` key with different semantics, either narrow the normalization or make it in-memory only** — this is the one case where "additive, never destructive" does not hold.
- **`useSprints()` backfills each sprint's `tabGrid` against the schema's current tabs in the hook's RETURN value (a `useMemo`), not just once at mount**: the schema can gain a tab after the hook already mounted (live schema editor, another tab via the `storage` event), and the initial `useState` backfill only ever runs once. Deriving the "every sprint has a grid for every schema tab" invariant on every render — without touching `sprints` state or the persistence effect — means a freshly added tab is immediately writable instead of showing 0 rows until a reload. `updateGridCell`/`moveRow` read the raw state through the same fallback (`gridFor`), so the very first edit on a newly materialized tab is never a silent no-op either.
- Editable spreadsheet grid (20 rows per tab by default), resizable columns, drag-and-drop rows, Ctrl+click ticket links, keyboard navigation, SnapLink paste support
- **Columns/tabs editor**: a "Pestañas y columnas" text button (`schema.sprintOpen`) above the grid opens `SprintSchemaEditor.tsx`. Unlike `RegressionSchemaEditor`, it lists ALL tabs at once — not just the active one, since `activeTab` is `TrackerGrid`'s own internal state and pulling it out for the editor to read would be far more invasive than just listing all five — each with its columns nested underneath, via the shared `SchemaEntryRow.tsx`: rename (local draft commits on blur, same as Regression's editor), add, hide, no Save button, writes go straight to `acgen_schema`. A new tab starts with a CLONE of the first default tab's columns (never the live `DEFAULT_SCHEMA` reference) so it's never born with nothing to show. A guard blocks hiding the last visible tab, or the last visible column within a tab. "Restaurar por defecto" resets only the `sprint` section — the merge-on-write `useSchema()` fix from Fase 4's final review already protects the `regression` section from this button, and the reverse now holds too.
- Sprint list: "Editar" button on active (non-archived) sprint cards renames the sprint inline (input replaces the name, Enter/blur saves, Escape cancels, empty name is a no-op); "Archivar" button (also active-only) archives from the list after a `confirm` — same `archiveSprint` + `sprint.archiveConfirm` the dashboard's "Archivar Sprint" button uses. Active cards: 🟢 + "En curso"; archived cards: 🔴 + singular "Archivado" badge (`sprint.archivedBadge` — `sprint.archived` stays plural for the section header), no Editar/Archivar buttons

### Regression Tracker

- Fully offline — no LLM dependencies
- **Versioned regressions, not a free grid**: platform tabs and ticket-table columns both come from `useSchema()` (`src/hooks/useSchema.ts`, `src/types/schema.ts`) rather than being hardcoded. With nothing saved to `acgen_schema` the tabs and columns are exactly today's: APPS (internal id `ios`, label "APPS") and WEB (internal id `webDesktop`, label "WEB") — internal ids kept historical so existing localStorage data survives renames — and the ticket fields Ticket/Fecha/Prioridad/Creador/Squad/Status. A `SchemaEntry`'s `id` is a storage key that **never changes**; renaming writes a literal `label` that wins over the default `labelKey` translation (a renamed column reads the same in ES and EN); hiding an entry only sets `hidden` and never deletes its data — a hidden ticket field stays on every stored ticket, a hidden platform's regressions stay under `regressions[id]`, and both come back exactly as they were the moment the entry is shown again. Fields and platforms removed from the schema this way (or from an older, smaller schema) are kept but orphaned — same "huérfano pero intacto" convention the legacy `board` already uses. Each tab is a list of `Regression { version, url, fecha, tickets[] }` cards, newest first; "+ Nueva regresión" creates one with 3 empty ticket rows (version required, url/fecha optional)

"+ Añadir ticket" appends rows; the per-row × asks `confirm` only when the row has any content (an empty row deletes silently). The "Nombre - URL" link-cell rendering (name overlay at rest, full value on focus, Ctrl+click or the ↗ icon opens it, via the shared `src/utils/trackerLinks.ts#parseUrlCell`) is applied to the **first visible column**, not to a hardcoded `ticket` field id — under the default schema that's the same cell as before, but the behavior survives renaming or hiding earlier columns. **Columns editor**: a "Columnas" text button in the tab bar (plain text, not a ⚙ icon — `TrackerGrid` already uses ⚙ for the tracker base URL) opens `RegressionSchemaEditor.tsx`, which lists both the ticket fields and the platforms via `SchemaEntryRow.tsx` — rename, add and hide, each writing straight to `acgen_schema` with no Save button (the rename input alone keeps a local draft that commits on blur, so clearing it to retype can't wipe the label). Adding works identically for ticket fields and platforms (same UUID id, appended to the end of its list, empty name is a no-op) — a team testing iOS and Android natively is no longer capped at the two default tabs. A guard blocks hiding the last visible entry of either list. "Restaurar por defecto" resets only the `regression` section of the schema; `useSchema()`'s write path merges every write against what's actually stored (not just what this phase's `schema` return value knows about), so any section a later phase adds (e.g. Fase 5's `sprint`) survives untouched through resets, renames or any other schema write, not only the reset button
- **Per-regression archiving**: "Archivar" on a card asks `confirm`, then moves that single regression (not the whole tab) into `archived` as `{ id, archivedAt, platform, regression }`, labeled `"<platform label> · <version>"` in the history list — the label is resolved from the schema's current platform entry, so a renamed platform relabels its old archived entries too, and one whose entry was hidden or removed still resolves (falling back to the raw platform id, never a blank label); opening it renders the same `RegressionCard` read-only and already expanded (no Editar/Archivar/Eliminar, ticket inputs readOnly)
- **Mixed history**: `archived` is a discriminated union (`isLegacyArchived()` checks for a `board` key) — old-style archived snapshots from the pre-2026-08-10 free 20×6 grid still open with the legacy read-only `TrackerGrid` (headers Regresión/Versión/Fecha/Notas/Status). The pre-migration live board itself (top-level `board` key in `acgen_regressions`) is hydrated and re-persisted intact but is **never rendered** anywhere — it exists only so round-tripping through the app doesn't lose that orphaned data
- **Drag & drop reorder**: each card header carries a ⠿ handle (native HTML5 drag, no libraries) — dragging over another card shows a top/bottom insertion indicator and dropping calls `moveRegression(platform, id, toIndex)` (index clamped, unknown id no-op); the array order IS the persisted order. Handles are hidden while a search is active and never rendered in readOnly snapshots. jsdom lacks `DragEvent`, so `src/test/setup.ts` carries a minimal test-only polyfill (jsdom#2913)
- **Search with match highlighting**: a 440px search field (right of "+ Nueva regresión", ×-clearable, "N / M" counter, query survives tab switches) filters the ACTIVE tab case-insensitively against version, url and the schema's **visible** ticket fields only — a hidden field's stored value can't surface a match (deliberately narrower than the Sprint Tracker's search, which DOES match hidden columns — see "Sprint Tracker" above and "Known issues"). **Fases 4 y 5 de productización están hechas, mergeadas y en producción** — cada una con su fila propia en "Evolution history" más abajo, donde vive el detalle. La Fase 5 se verificó además con 27/27 asertos en navegador real contra producción (`scripts/browser-checks/`, ver su README).

Comportamientos deliberados del Sprint Tracker en producción, no defectos ni pendientes:

- **Sprint tabs and columns can't be deleted or reordered** — the Sprint Tracker's grid is positional (a column's `dataIndex` IS its on-screen position and every stored width is keyed by that index), so either operation would require migrating the grid to keyed rows plus migrating stored widths from index-keyed to id-keyed. Hiding an entry already covers the practical case: the data survives and the entry can be shown again exactly as it was, same as Regression Tracker fields/platforms.
- **Renaming a Sprint tab or column fixes the text in both languages, same tradeoff as Fase 4's Regression Tracker**: writing a literal `label` wins over the default `labelKey` translation, so a renamed tab/column reads identically in ES and EN — there is no way to give it two different per-language labels once renamed.
- **The schema is global — archived sprints are read through it too, so a historical view is not immutable.** There is exactly one `acgen_schema`, shared by every sprint; renaming or hiding a column changes how an already-archived sprint reads, not just the live one. No data is lost (hiding never deletes: the value stays in the sprint's `tabGrid` at its `dataIndex` and comes back the moment the column is shown again), but the archived sprint you open next month may be labelled differently, or be missing a column, versus what it looked like when it was archived. Freezing a per-sprint copy of the schema at archive time would fix it and is deliberately not done in this branch. **Archived sprints are now genuinely read-only** (2026-08-15, follow-up branch): `SprintDashboard` passes both `dragDisabled` and `readOnly`, so cells aren't editable, "+ Fila" is gone and the schema editor button is hidden — before this, only row drag-and-drop was disabled and you could silently corrupt a closed sprint by typing in a cell. It ships together with **Desarchivar** (`unarchiveSprint`, clears `archived` and `endDate`) because archiving used to be one-way: freezing a sprint with no way back would have left a typo spotted after closing it stuck forever. Known trade-off: `TrackerGrid` makes column widths ephemeral in `readOnly` (same as the Regression Tracker's legacy snapshots), so resizing an archived sprint's columns no longer persists between visits.
- **Across browser tabs the schema syncs but the sprint data does not — pre-existing, slightly widened by Fase 5.** `useSchema` sits on `useLocalStorage`, which listens to the native `storage` event, so a schema change in one browser tab reaches the others. `useSprints` does not: it holds `acgen_sprints` in a plain `useState` hydrated once at mount, with no `storage` listener, so a second browser tab keeps a stale sprints array and its next edit persists that stale state over whatever the first tab wrote. Fase 5 doesn't introduce this, but it does widen the window a little: the second tab now immediately shows a column the first tab just added and invites the user to type in it. The fix would be a `storage` listener in `useSprints` (or moving it onto `useLocalStorage`), out of scope here.
- **The two trackers' searches deliberately disagree about hidden columns — NOT an inconsistency to fix.** Full reasoning, Jorge's 2026-08-15 decision and the tests that pin it: see "Sprint Tracker" above. Mentioned here only so nobody reaches this list, spots the difference and "fixes" it.

Pending items, none blocking a release. Todos verificados contra el código el 2026-08-16 (auditoría de cierre de la cacería): siguen vigentes, ninguno está ya resuelto.

Hoy no hay camino que llegue ahí (exige un `acgen_schema` editado a mano), pero **antes de que una fase futura reutilice la clave `columns` con otra semántica hay que acotar la normalización o hacerla solo en memoria**.
